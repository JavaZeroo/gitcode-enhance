# 2026-11-03 内存优化验证

本报告对应发布前的测量源码（当时内部版本为 0.3.3），记录未使用图标改存 SVG 文本、讨论区按阅读位置展开两项优化。代码已纳入 v0.3.4；测量时的源码 SHA-256 保留不变，渠道状态见[发布记录](../releases/v0.3.4.md)。

## 改动和边界

- 图标缓存不再强引用已移除的 `<symbol>`，原容器通过 `WeakRef` 记录，已处理容器通过 `WeakSet` 记录。原容器仍在页面时恢复到原位置；容器已被移除时，新建隐藏 SVG 容器恢复缓存图标。缺少 `WeakRef` 或页面禁止 SVG 字符串解析时，保留原生图标，不执行裁剪。
- 讨论区只检查少量原生折叠按钮，默认处理视口内及下方 320px 范围。滚动/窗口变化后合并调度，每 500ms 最多一次；后台暂停，离开路由或取消时移除监听和待执行任务。设置中可选择「全部折叠消息」。
- 每个折叠按钮只自动尝试一次，失败后仍可手动点击。单个按钮可能由站点一次展开很多消息；本次未拆分站点内部数据，也不收起已展开内容，不能保证看完全部评论后仍省内存。

## 对照方法

之前实页 profiling 发现 1561 个未使用 symbol、4745 个后代节点仍被 Map 保留；这轮使用隔离 Chrome 验证引用释放，不将合成数据冒充实页测量。

环境：Windows，Node 24.22.2，Chrome 156.0.8078.80。每次启动独立浏览器与临时用户目录，页面和脚本来自本机 HTTP fixture，不连接用户的浏览器、登录态或站点接口。执行真实源文件中的图标和展开函数，截断 UI/bootstrap；因此不覆盖 Tampermonkey 沙箱与真实站点生命周期。

图标 fixture 为 1600 个 symbol，每个含两个 path，共 4800 个节点，SVG 文本 1,322,180 字符。每个检查点间隔一个任务，并调用两次 `HeapProfiler.collectGarbage`；用 `WeakRef` 观察原节点与原容器是否存活，同时读取 DOM 计数与 CDP 堆指标。再恢复 200 个图标，检查文本往返和绘制几何；移除原容器后引用另一个缓存图标。

展开 fixture 放置近处与 6000px 处的按钮。等待 1200ms，覆盖两轮自动点击机会；再滚动到远处，最后取消并添加新按钮。它验证调度行为，不测真实评论的内存占用或服务器加载时间。

原实现执行优化断言时失败：`Unused original symbol DOM must be collectable`，实际仍存活 1600 个。修改后相同断言通过。最终对照原始指标及源文件 SHA-256 见 [JSON](2026-11-03-memory-summary.json)；中间样本和优化前源码保留于被忽略的本地目录 `memory-2026-11-03/`。

## 最终对照结果

| 强制 GC 后的检查项 | 修改前 | 修改后 |
|---|---:|---:|
| 存活的原始未使用 symbol | 1600 | 0 |
| 裁剪后文档 DOM 节点计数，含脱离文档但仍存活节点 | 4810 | 10 |
| 原图标容器从页面移除后是否仍存活 | 是 | 否 |
| 原容器移除后引用缓存图标，是否恢复且有绘制几何 | 否 | 是 |
| 裁剪后 `usedSize` | 890,848 B | 847,512 B |
| 裁剪后 `embedderHeapUsedSize` | 4,312,960 B | 306,384 B |
| 裁剪后 `backingStorageSize` | 255,288 B | 1,415,029 B |
| 初始等待后，远处按钮是否自动展开 | 是 | 否 |
| 滚到远处后是否展开 | 是 | 是 |

这些是不同内存域的协议指标，不相加当作进程内存。结果证明原 DOM 对象可回收；字符串存储增加是预期代价。没有测浏览器进程 RSS、完整实页的堆快照保留大小或统计分布，不能宣称整页节省固定 MB/百分比。

最终对照中，一次裁剪耗时 13.8ms → 23.8ms，恢复 200 个图标耗时 2.8ms → 6.4ms。前面的探索样本有波动：修改前裁剪 8.7～12.2ms，修改后 16～25.9ms；恢复计时也出现过 23.9ms 的调度波动。序列化和重新解析需要额外工作，本轮优化的是长期节点保留，不能称为该操作更快。裁剪仍沿用页面加载后的空闲调度，未新增启动阶段的同步裁剪。

## 正确性验证

- Node 回归测试 25/25 通过，覆盖附近/远处按钮、后台暂停、重新开始、路由取消、隐藏按钮、显式全部展开，以及解析不可用时不裁剪。
- 独立 Chrome 优化断言通过：原节点回收、移除容器回收、后续恢复、滚动后展开、取消后不再点击。
- 200 个恢复图标的 SVG 文本完全一致，绘制几何宽度大于零。
- 复杂图标的转义文字、渐变、`clipPath`、嵌套 `use` 与 xlink 命名空间往返正确；普通 `href` 修改能恢复新目标。引用节点的计算颜色随父元素从红色改为蓝色，未做真实站点主题切换的像素级对照。
- 发现旧有边界：仅通过 `setAttributeNS` 动态修改 `xlink:href` 时，新旧实现均未恢复目标；新增含 xlink 引用的节点正常。本次未扩大全页属性监听，问题已加入 TODO。

## 复现

在仓库根目录执行（结果文件放在已存在的临时目录即可）：

```powershell
npm test
node scripts/profile-memory.mjs 'C:/Program Files/Google/Chrome/Application/chrome.exe' src/gitcode-enhance.js "$env:TEMP/gitcode-memory-check.json" --expect-optimized
```

`scripts/profile-memory.mjs` 只启动和关闭自己创建的浏览器，结束后删除经路径校验的临时配置目录。若比较其他版本，第二个参数换成对应源文件；不加 `--expect-optimized` 可保存修改前测量。

完整实页的 PR 回复框可用时间、图标主题切换、快速滚动与登录环境验收仍待补充，本轮不能宣称历史回复框问题已彻底解决。源码、两份构建产物及旧路径开发脚本同步后，刷新使用本地加载器的 GitCode 页面即可应用；正式安装版不会自动取得本地改动。
