# 2026-11-03 性能剖析与已验证修复

本文保留发布前测量时的版本与验证结果，修复已纳入 v0.3.4；渠道状态见[发布记录](../releases/v0.3.4.md)。此前的探索性记录见 [2026-11-03.md](2026-11-03.md)，本次增加实际 Chromium 时间线、CPU 采样调用栈、单变量实验和缓存生命周期检查。

## 最重要的结论

脚本的四条 `html:has(#gce-review-tools...)` 规则会放大 PR 讨论页的样式计算。站点 `FoldEllipsis` 组件为测量文字高度，反复插入临时 span 并同步读取尺寸；全页关系选择器使这一过程非常昂贵。即使讨论页没有评审工具，这些规则也存在。

已改为由评审工具挂载、专注模式切换和卸载显式维护 `gce-review-page` / `gce-review-focus` class。没有修改站点的文字测量组件，也没有为了这次对照关闭自动展开。

### 相同时间窗口的证据

场景：[Ascend/pytorch PR 48352](https://gitcode.com/Ascend/pytorch/pull/48352)。从主文档 `CommitLoad` 开始截取 **10,000 ms**，排除服务器返回 HTML 前的等待。只统计对应主框架线程的 `UpdateLayoutTree`；跨类别的嵌套耗时不可相加。

| 样本 | 原规则：样式重算 | 修复后：样式重算 |
|---|---:|---:|
| 第一次 | 4,640.73 ms | 1,399.86 ms |
| 第二次 | 5,301.87 ms | 1,327.05 ms |
| 均值 | 4,971.30 ms | 1,363.46 ms |

该窗口内样式计算均值下降 **72.6%**。这不是 FCP、整页加载时间或全站提速百分比。样本量为每种配置 2 次，属于定位证据，未达到 ROADMAP 的正式发布基准要求。

原规则两次采集分别发生 20 秒、45 秒的采样命令超时；仍保留了时间线。完整记录中的样式重算分别累计约 14.95 秒和 48.96 秒，观察时长不同，所以不能直接拿它们与修复版的 12 秒记录求加速比。上表使用离线统一截窗解决这一问题。

单变量验证还包括：只关闭自动展开时样式重算约 1.87 秒；保留自动展开、只替换全页关系选择器时约 1.27 秒（均为约 12 秒加载采样）。这解释了为什么仅限制重复点击还不够。另做过原地增删旧规则的微基准，但移除后开销没有立即恢复，存在顺序效应，未用于计算收益。

站点热点来源为已加载的 `DvxD56ww.js` 中 `FoldEllipsis` 的 `i` 函数，及 `BMF51KPO.js` 中读取容器高度的 MutationObserver。它们反映了同步样式/布局的触发位置，不能据此把全部成本归咎于站点代码；脚本规则的单变量对照才提供了归因证据。

## 加载场景与剩余瓶颈

所有开关样本使用独立测量标签页的 sessionStorage 门控，不修改用户全局设置。实际开启配置为 aggressive。采用普通缓存刷新，无网络/CPU 节流，不清空登录态或站点缓存。

| 场景 | 观测 | 判断与下一步 |
|---|---|---|
| 登录后的工作台 `/dashboard/latest-activity` | 关闭/开启/开启/关闭四次；TTFB 为 4265 / 593 / 154 / 180 ms | 网络等待波动足以淹没脚本收益，不能用单次 load 对比宣称首页提速 |
| 工作台 DOM | 停用约 5793 个元素，开启约 447 个 | 裁剪确实减少活跃 DOM；这不是堆内存释放证明 |
| PR 讨论页 | 修复后仍有约 1.33～1.40 秒批量渲染长任务 | 优先评估自动展开的按需/分批调度，并保留手动入口 |
| PR 10 差异页 | 22 文件、提交 `bb9ab148`；停用 FCP 2684 ms，修复版两次 1832 / 2012 ms | 样本不足，且 TTFB/缓存/扩展有干扰，不能把差值当稳定加速 |
| 差异工具启动 | 两次 userscript idle 回调累计约 218 / 174 ms | 下一步拆分首次扫描、DOM 写入和 `trackCurrent()` 尺寸读取，确认强制布局贡献 |
| 网络 | 讨论页同一 `getRuleset` 路径出现两次，记录中一次约 4.34 秒完成；diff 一次约 2.42 秒 | 时间线包含主线程回调延迟，不能直接称为服务器耗时；也未验证两次请求参数是否相同，不应直接加缓存 |
| 拦截时机 | aggressive 下仍有 `captcha-executed=true` 与晚到脚本 | 需单独验证正式安装版注入时机；不能把尝试拦截的数量当下载节省 |

推荐页 `/?p=seo` 有探索性记录，但独立测试标签页随后转到工作台；这类跨路由样本不纳入首页 A/B。仓库首页、冷缓存和其他机器本轮没有覆盖。

差异页时间线中其他浏览器扩展也有明显开销，包含自动化扩展的 DOM 读取；没有关闭用户扩展。当前结果适合查找机制，不代表纯净浏览器的绝对耗时。

## 内存和搜索：实际保留了什么

本节记录优化前的实页探针。后续已在本地实现 SVG 文本暂存和按阅读位置展开；强制 GC 的独立浏览器对照与限制见[内存优化报告](2026-11-03-memory.md)，不与本节实页样本混算。

在 PR 10 的测量标签页中，通过临时只读聚合探针检查脚本私有缓存，未导出评论内容：

- 图标 stash 实际保留 **1561 个 symbol、4745 个节点**。这些对象已经离开可见 DOM，但仍被 Map 强引用；序列化后共 **1,415,313 字符**。它是明确的长期保留点，不是已经证明的泄漏。图标统计与 stash 数量可能受重名 symbol 覆盖影响，不能仅依赖 UI 的移除计数。
- 首次搜索前无差异索引缓存。搜索 `Qwen` 后覆盖 **22/22 文件、867 行、46 条匹配行**；`text` 与 `lowerText` 合计 **63,460 字符**。这个样本的索引不大，暂时没有证据支持优先引入 Worker。
- 可见代码中建立了 8 个全局词高亮 Range；下一处能定位到新增侧第 8 行。关闭后高亮注册表立即清空。
- 关闭时仍保留一分钟复用缓存；约 **122 秒后**检查，缓存为 null、文件/行/字符计数均为 0。验证了清理结果，没有测得“恰好第 60 秒”的时刻。
- 这次搜索会话包含首次打开、输入、下一处、关闭；调用栈能看到打开、清理及滚动回调，没有显示出重型索引瓶颈。没有测完整输入到结果延迟分布，也没有覆盖十万行或超大单文件。

`Runtime.getHeapUsage` 原始值已保存，但不同刷新之间 GC 和旧文档回收时点不同。本次接口无法强制 GC，没有 heap snapshot 的 retained-size 证据，也未测浏览器进程总内存。因此**不宣称减少了多少 MB，更不把刷新后堆增长直接称为泄漏**。

## 优化顺序与验收

| 优先级 | 优化点 | 验收信号 |
|---|---|---|
| P0，已本地修复 | 移除根元素上的全页关系选择器 | 固定窗口样式重算下降；专注模式、跳转间距和离开 diff 后的恢复正常 |
| P1 | 自动展开按需进行，避开首屏和密集状态更新 | 编辑器可用时间、最大长任务与动态数量同时记录；不遗漏内容、不丢失回复入口 |
| P1 | 图标 stash 评估序列化存储，恢复时再构建节点 | 强制 GC 后的保留对象/字节下降，主题切换和新图标恢复无回退；暂不直接上线 |
| P1 | 差异工具初始化分离 DOM 写入与布局读取 | 首次回调不再形成长任务；当前文件跟踪与跳转正确 |
| P2 | 大 PR 搜索按数据规模设缓存预算，必要时 Worker | 十万行、长行和快速连续输入的延迟/峰值内存；不能用当前 867 行样本外推 |
| P2 | 重新核验非必要请求的实际拦截效果 | 只统计真正避免的请求，验证登录/风控/PR 状态；不扩大默认拦截范围 |

## 复核数据和方法

可共享的数字摘要：[2026-11-03-profiling-summary.json](2026-11-03-profiling-summary.json)。完整本地证据在 `docs/performance/profiling-2026-11-03/`，含可导入 DevTools 的 `*-trace.json`、`*-metrics.json`、分析输出和现场站点 bundle；体积较大且未全面脱敏，已加入 gitignore，未上传。

离线复算示例（在仓库根目录执行）：

```powershell
node scripts/analyze-profile.mjs --window-ms=10000 docs/performance/profiling-2026-11-03/discussion-on-repeat-trace.json docs/performance/profiling-2026-11-03/discussion-fixed-2-trace.json
```

采集使用 `Tracing.start` 的 `devtools.timeline,v8.execute,disabled-by-default-v8.cpu_profiler`，从 reload 前开始，通常在导航开始约 12 秒时收集页面指标并结束。用 `Profile` 对应主线程，按 process/profile ID 合并 `ProfileChunk`；V8 负 timeDelta 先还原采样时间再排序，避免重复计时。CPU 采样是估计值，根因对照的主要数字取时间线事件时长。

有 `CommitLoad` 的记录只分析最外层主框架线程，不把另一 renderer 的空闲时间算进主页面。PR 的 Resource Timing 达到默认 250 条上限，故请求分析使用时间线的发送/响应/完成事件（例如讨论修复第二轮 283 次，diff 修复第一轮 320 次），不把 250 当完整总数；跨域 transferSize=0 也不视为零流量。

超时首轮的事件恢复缓冲混有此前采集，已按最后一个 Profile 起点保留对应时间线；`missingSampleNodes=0`。探索性首页、跨路由、变长窗口及原地样式微基准分别标明用途，不合并求总收益。
